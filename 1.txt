轻量级多设备文件同步与版本存储系统

完整技术设计方案（V1.0）

文档状态： 初步技术设计
设计目标： 构建一个轻量级、跨平台、多设备、支持离线同步和历史版本恢复的私人文件同步系统。
核心架构： 本地设备为主要存储节点，VPS 为协调节点、数据中继节点和有限容量的辅助存储节点。


---

1. 项目概述

1.1 项目背景

本项目希望解决以下问题：

1. 用户拥有一台具有公网 IP 的 VPS，但 VPS 磁盘空间有限。


2. 用户拥有多台本地电脑，电脑具有较大的存储空间，但通常没有公网 IP。


3. 多台电脑可能处于不同网络环境，无法直接访问彼此。


4. 当某台电脑关机时，其他电脑产生的文件变更仍然需要保存。


5. 用户希望能够保留文件的多个历史版本，在误删或误修改后恢复旧版本。


6. VPS 资源有限，不希望部署复杂的数据库、Web 管理面板和大量后台服务。



因此，本项目不采用传统的中心化云盘架构，而采用：

P2P 文件同步 + VPS 协调服务 + VPS 有限容量缓存 + 多版本存储。

1.2 核心设计理念

系统遵循以下原则：

本地电脑是主要文件存储位置。

VPS 不需要保存所有电脑的完整文件。

设备之间优先直接传输文件。

无法直接连接时，可以通过 VPS 中继。

原始设备离线时，可以从 VPS 获取已缓存的更新。

VPS 可以保留最近 N 个文件版本。

用户可以自行设置 VPS 存储容量上限。

不需要 Web 管理面板。

客户端负责主要的文件扫描、同步和冲突处理工作。

VPS 尽可能保持轻量。

2. 系统总体架构

2.1 架构组成

系统分为三个主要部分：

1. Client：设备客户端。


2. Server：VPS 协调服务。


3. Storage：VPS 对象存储。



整体结构：

VPS
    ┌──────────────────────────────┐
    │                              │
    │       Lightweight Server     │
    │                              │
    │  ┌────────────────────────┐  │
    │  │ Device Manager         │  │
    │  ├────────────────────────┤  │
    │  │ Discovery Manager      │  │
    │  ├────────────────────────┤  │
    │  │ Message Manager        │  │
    │  ├────────────────────────┤  │
    │  │ Relay Manager          │  │
    │  ├────────────────────────┤  │
    │  │ Storage Manager        │  │
    │  └────────────────────────┘  │
    │                              │
    │  ┌────────────────────────┐  │
    │  │ SQLite Metadata       │  │
    │  ├────────────────────────┤  │
    │  │ Object Storage        │  │
    │  └────────────────────────┘  │
    │                              │
    └──────────────┬───────────────┘
                   │
           Internet / Network
                   │
        ┌──────────┴──────────┐
        │                     │
   ┌────▼─────┐          ┌────▼─────┐
   │ Client A │◄────────►│ Client B │
   └──────────┘   P2P    └──────────┘
        │                     │
   Local Files           Local Files

设备之间优先建立 P2P 连接。

如果 P2P 连接失败，则尝试使用 VPS Relay。

如果某台设备离线，则其他设备可以从 VPS Storage 获取已缓存的数据。

2.2 数据传输优先级

建议采用以下顺序：

优先级	传输方式	使用场景

1	P2P 直连	两台设备都在线且可以建立连接
2	VPS Relay	两台设备在线，但无法直接连接
3	VPS Storage	目标设备离线，需要稍后同步


这样可以尽量减少 VPS 的带宽和流量消耗。

3. 客户端设计

客户端是整个系统的核心。

每台电脑安装一个后台客户端，负责监控文件变化、维护本地状态、连接其他设备以及处理同步任务。

3.1 客户端主要模块

模块	功能

File Watcher	监控文件变化
Scanner	扫描指定目录
Hash Engine	计算文件或数据块 Hash
Local Index	保存本地文件索引
Version Manager	管理文件版本
Sync Engine	决定上传和下载任务
P2P Manager	管理设备间连接
Storage Client	与 VPS 存储服务通信
Conflict Manager	处理文件冲突
Encryption Manager	负责加密和解密


3.2 文件监控

客户端需要支持不同操作系统的文件监听机制。

操作系统	文件监听机制

Windows	ReadDirectoryChangesW
Linux	inotify
macOS	FSEvents


文件监听用于快速发现变化。

但是文件系统事件可能丢失，因此还需要周期性扫描。

建议：

文件事件监听：实时触发。

周期性扫描：定期检查文件状态。

启动扫描：客户端启动时检查同步目录。

断线恢复扫描：网络重新连接后检查版本差异。


文件监听只负责发现变化，最终状态以文件扫描和版本校验结果为准。

3.3 本地数据库

客户端使用 SQLite 保存本地索引。

建议保存：

文件路径。

文件大小。

修改时间。

文件 Hash。

文件版本。

对象引用。

当前 Snapshot。

已同步设备。

待处理任务。

文件冲突记录。


客户端必须具备断网工作能力。

即使 VPS 暂时不可用，客户端仍然可以：

修改文件。

记录文件变化。

创建本地版本。

等待网络恢复后同步。

4. VPS 服务端设计

VPS 不需要负责文件扫描和文件同步的核心逻辑。

它主要负责设备协调、数据中继和有限容量的数据存储。

4.1 Device Manager

负责设备身份管理。

主要功能：

设备注册。

设备认证。

设备列表。

设备在线状态。

设备授权。

设备撤销。

设备密钥管理。


每台设备需要具有独立身份。

建议采用设备密钥和证书进行身份验证。

不能仅依靠设备名称或普通设备 ID 判断身份。

4.2 Discovery Manager

负责设备发现和连接协调。

主要功能：

记录设备网络地址。

交换设备连接信息。

发现在线设备。

协调 NAT 穿透。

协助建立 P2P 连接。


需要注意：

NAT 穿透并不能保证所有网络环境下都成功，因此必须保留 Relay 方案。

4.3 Message Manager

负责设备之间的状态通知。

例如：

Device A:
    New Snapshot Available

VPS:
    Notify Device B

Device B:
    Request New Snapshot

VPS:
    Return Version Information

消息内容可以包含：

设备 ID。

同步目录 ID。

Snapshot ID。

新版本信息。

对象列表摘要。

同步状态。


消息服务不能作为唯一的数据同步依据。

客户端重新上线时，必须主动向 VPS 查询最新版本，防止遗漏通知。

4.4 Relay Manager

当两台设备无法直接建立 P2P 连接时，VPS 可以中转数据。

建议支持：

Relay 开关。

最大并发连接数。

最大带宽。

单设备流量限制。

超时断开。

连接认证。


Relay 只负责转发，不需要长期保存数据。

4.5 Storage Manager

这是本项目区别于普通 P2P 同步工具的重要模块。

负责：

接收客户端上传的对象。

验证对象完整性。

保存文件数据。

保存版本元数据。

管理存储配额。

管理对象引用。

执行垃圾回收。

提供离线设备的数据下载。


VPS 的 Storage Manager 不应该复制整个本地文件目录。

它只需要保存对象和必要的版本信息。

5. 文件存储与版本管理设计

这是整个项目最重要的部分之一。

建议采用：

内容寻址存储（CAS）+ 分块存储（Chunking）+ Snapshot 版本模型。

5.1 内容寻址存储

每个文件或数据块通过 Hash 标识。

例如：

report.docx
    |
    v
BLAKE3
    |
    v
a81f0c...

存储时不直接使用原始文件名作为对象标识，而是使用 Hash。

这样可以实现：

相同内容只保存一次。

不同文件可以共享相同数据对象。

文件重命名不需要重新上传。

历史版本可以共享未变化的数据。


建议第一版采用 BLAKE3，协议中保留 Hash 算法版本字段。

5.2 分块存储

大文件不建议始终作为一个完整对象处理。

可以把文件拆成多个 Chunk。

例如：

1GB File
   |
   +-- Chunk 001
   +-- Chunk 002
   +-- Chunk 003
   +-- Chunk 004
   +-- ...

每个 Chunk 独立计算 Hash。

文件版本只需要保存 Chunk 的排列关系。

建议研究 FastCDC 等内容定义分块算法。

相对于固定大小分块，内容定义分块能够更好地处理文件中间插入或删除数据的情况。

第一版可以先实现整文件对象存储，待基本同步稳定后再加入分块去重。

5.3 Snapshot 版本模型

参考 Git 的对象结构，但不直接使用 Git 作为同步引擎。

建议设计以下数据类型：

数据类型	功能

Blob	实际文件数据
Chunk	文件数据块
Tree	目录结构
Snapshot	某一时刻的目录状态
Ref	当前设备或同步目录指向的版本


例如：

Snapshot V3
    |
    +-- Tree: Documents
    |       |
    |       +-- Blob: A.docx
    |       +-- Blob: B.jpg
    |
    +-- Tree: Projects
            |
            +-- Blob: main.go
            +-- Blob: config.json

每次文件发生变化，只需要生成新的对象和新的 Snapshot。

未变化的数据继续引用旧对象。

5.4 多设备版本分支

不同设备可能同时修改文件。

因此不能简单地使用一个全局最新版本覆盖所有设备。

建议每台设备维护自己的版本引用。

例如：

Snapshot V1
               /       \
              /         \
        Device A       Device B
            |               |
        Snapshot V2     Snapshot V3

当两台设备产生不同修改时，系统需要比较版本祖先关系。

如果可以安全合并，就合并。

如果无法安全合并，则保留冲突副本，不允许静默覆盖。

6. 历史版本保留策略

6.1 核心需求

系统必须支持：

每个文件保留最近 N 个历史版本，N 由用户配置。

例如：

version_retention:
  enabled: true
  max_versions: 10

这里的 max_versions 包含当前版本。

某个文件产生 12 个版本：

V12  ← 当前版本
V11
V10
V9
V8
V7
V6
V5
V4
V3
V2
V1

系统保留：

V12
V11
V10
V9
V8
V7
V6
V5
V4
V3

超过数量限制的旧版本进入回收流程。

6.2 按文件夹设置版本数量

建议支持全局默认配置和文件夹独立配置。

例如：

version_retention:
  enabled: true
  default_max_versions: 10

  folders:
    Documents: 20
    Projects: 50
    Photos: 5
    Downloads: 2

如果某个文件夹没有单独设置，则使用全局默认值。

需要明确：这里的 N 按文件的历史内容版本计算，而不是简单按整个目录的 Snapshot 数量计算。

目录 Snapshot 负责记录目录整体状态，文件版本记录负责实现每个文件独立的 N 版本保留。

6.3 版本恢复

客户端需要提供恢复能力。

例如：

report.docx

当前版本：
V10

历史版本：
V9
V8
V7
V6
V5

用户选择 V7 恢复后：

系统不能直接破坏历史记录，而应该基于 V7 的内容创建一个新的当前版本。

例如：

V10 → 当前
V11 → 恢复自 V7

这样历史记录保持连续，也便于追踪恢复操作。

6.4 删除文件后的历史版本

删除文件不能立即删除其历史版本。

建议：

删除操作生成 Tombstone（删除标记）。

删除标记参与目录 Snapshot。

在保留期限内，历史内容仍然可以恢复。

超出版本保留范围后，才允许回收不再被引用的对象。

7. VPS 存储空间管理

7.1 存储配额

用户可以设置 VPS 最大存储容量。

例如：

storage:
  enabled: true
  quota: 20GB

  version_retention:
    enabled: true
    max_versions: 10

  garbage_collection:
    enabled: true
    interval: 6h

配额是实际存储空间的硬限制。

系统需要统计：

已使用对象空间。

临时上传空间。

待提交对象空间。

保留历史版本所引用的空间。

可回收对象空间。


不能只统计已提交对象而忽略正在上传的临时文件，否则并发上传可能突破配额。

7.2 存储策略

建议第一版采用：

待同步缓存 + 最近 N 个版本保留。

也就是说：

1. 尚未被目标设备获取的变更需要保留。


2. 最近 N 个文件版本按照保留规则保存。


3. 已经超出保留范围且没有其他引用的对象可以回收。


4. 不需要保存完整的本地文件副本。



未来可以扩展：

指定文件夹长期保留。

指定文件夹只保留最新版本。

指定文件夹保留更多历史版本。


7.3 存储空间不足时

假设 VPS 最大容量为 20GB，目前已经使用 19.8GB。

客户端需要上传一个 1GB 的文件。

系统应该：

1. 检查是否有可回收对象。


2. 执行垃圾回收。


3. 再次检查空间。


4. 如果空间仍然不足，则拒绝提交。


5. 返回明确的空间不足状态。


6. 客户端保留本地待同步任务。



不能在文件没有完整保存时向客户端报告成功。

8. 垃圾回收机制

建议采用基于对象引用关系的垃圾回收。

例如：

Object A
  ↑
  ├── Version 1
  ├── Version 2
  └── Version 3

当 Version 1 被删除时，Object A 仍然被 Version 2 和 Version 3 引用，因此不能删除。

只有当对象不再被任何有效版本、Snapshot、同步任务或其他保留策略引用时，才能回收。

建议垃圾回收分成三个步骤：

第一步：标记

检查对象是否仍被有效版本引用。

第二步：候选回收

把无引用对象标记为待回收。

第三步：实际删除

经过安全检查后，删除对应对象文件。

为避免并发问题，还需要考虑：

正在上传的对象。

正在下载的对象。

离线设备尚未获取的版本。

正在创建的 Snapshot。

正在执行的版本恢复操作。


建议使用延迟回收，而不是刚发现引用数为零就立即删除。

10. 文件冲突处理

多设备同时修改同一个文件是必须考虑的情况。

例如：

电脑 A:
report.docx → 修改为版本 A

电脑 B:
report.docx → 修改为版本 B

如果两个修改来自同一个旧版本，且无法安全自动合并，则不能直接覆盖。

建议采用冲突副本：

report.docx

report.conflict-deviceA.docx

具体命名应使用设备标识和时间，避免冲突副本本身重名。

第一版不建议实现复杂的 Office 文档合并功能。

优先保证：

不丢失任何一方的数据。

能够识别并记录冲突。

用户可以手动选择保留哪个版本。

解决冲突后生成新的 Snapshot。

11. 安全设计与端到端加密

建议系统从架构上支持端到端加密。

11.1 加密原则

文件内容在客户端加密后再上传 VPS。

电脑 A
   |
   v
本地文件
   |
   v
客户端加密
   |
   v
上传密文
   |
   v
VPS 保存密文
   |
   v
电脑 B 下载密文
   |
   v
客户端解密
   |
   v
本地文件

VPS 不应该拥有解密文件内容所需的用户密钥。

11.2 密钥管理

建议区分：

用户主密钥。

设备密钥。

文件或对象加密密钥。


用户主密钥负责保护设备间共享的密钥材料。

设备密钥负责设备身份认证。

文件加密密钥负责加密文件对象。

密钥管理必须考虑设备丢失、设备撤销、增加新设备以及密钥备份。

如果密钥丢失，历史密文可能无法恢复，因此密钥备份是重要功能。

11.3 元数据保护

端到端加密后，VPS 仍可能需要知道：

对象大小。

对象 ID。

版本引用关系。

所属设备。

存储状态。


如果希望尽量减少 VPS 可见的信息，还需要对路径、文件名和部分目录元数据进行加密。

需要注意：加密后，基于明文 Hash 的跨用户全局去重可能带来隐私风险。建议采用用户范围内的去重，不要为了节省空间而暴露跨用户文件是否相同。

12. 通信协议设计

建议客户端和 VPS 服务端统一采用 Go 实现。

协议需要支持：

设备认证。

心跳。

设备发现。

版本查询。

Snapshot 提交。

对象上传。

对象下载。

同步状态查询。

Relay 数据传输。

存储配额查询。


建议优先研究 QUIC/TLS。

不过需要特别注意：

QUIC 本身不等于完整的 NAT 穿透方案。P2P 连接仍需要地址发现、打洞协调、连接探测和失败回退机制。

因此网络模块应独立设计，避免把同步引擎与某一种传输协议绑定。

协议还应包含：

协议版本号。

对象格式版本。

Hash 算法标识。

加密算法标识。

请求 ID。

幂等性标识。

错误码。


这样以后修改传输层和对象格式时，不至于破坏已有数据。

16. 关键风险与解决方案

风险	解决方案

文件监听事件丢失	定期完整扫描
文件尚未写完就开始同步	稳定性检测、文件锁策略和重试
两台设备同时修改文件	版本祖先比较、冲突副本
上传中断	临时对象、断点续传
VPS 断电	SQLite 事务、原子提交
存储空间不足	配额检查、垃圾回收、明确失败状态
历史版本误删	对象引用检查和延迟回收
设备长期离线	保留未同步对象，支持重新上线后对账
Hash 不一致	下载后重新校验
VPS 泄露	客户端端到端加密
密钥丢失	密钥备份和恢复机制
NAT 穿透失败	Relay 回退


特别需要强调：

同步系统不等于完整备份系统。

如果所有设备都同步删除了一个文件，而 VPS 又按照保留策略清理了旧版本，那么数据仍可能无法恢复。

因此，版本保留、设备同步和独立备份应该是三个可以分别配置的功能。

18. 最终技术方案总结

本项目最终建议采用以下架构：

项目	设计决定

整体架构	P2P + VPS 协调 + VPS 辅助存储
客户端	Go 后台程序
服务端	Go 单进程
元数据数据库	SQLite
对象存储	本地文件系统
文件存储模型	内容寻址存储
数据去重	分块 Hash 去重
目录版本	Snapshot
文件版本	独立版本记录
历史保留	每个文件最近 N 个版本
N 的配置	全局默认 + 文件夹独立配置
历史恢复	创建新的当前版本
空间管理	VPS 可配置硬配额
垃圾回收	基于对象引用关系
网络传输	P2P 优先、Relay 回退
离线同步	VPS 缓存
安全	设备认证 + 端到端加密
Web 面板	不需要


最终架构原则

我认为整个项目应该坚持四个原则：

第一，本地设备优先。
用户的数据主要保存在自己的电脑上，VPS 不需要成为完整云盘。

第二，VPS 轻量化。
VPS 负责协调、发现、中继和有限存储，不承担繁重的文件扫描和同步决策。

第三，版本存储高效化。
采用内容寻址、分块去重和 Snapshot 引用，避免每个版本都复制完整文件。支持每个文件保留最近 N 个版本。

第四，数据安全优先。
文件同步不能静默覆盖，历史版本不能误删，VPS 不能在未完整保存数据时报告提交成功。

19. 下一步建议：先设计数据库和通信协议

在正式进入编码之前，建议先完成三个技术设计：

1. SQLite 数据库设计：明确 Device、Object、Chunk、FileVersion、Snapshot、Ref、SyncTask 等数据表。


2. 对象存储设计：明确对象命名、分块格式、加密格式、临时上传和垃圾回收机制。


3. 通信协议设计：明确客户端与 VPS 之间的注册、版本查询、对象上传、对象下载、提交和同步确认协议。



这三项确定之后，就可以开始搭建 Go 项目骨架。

我的建议是先完成 SQLite 数据库结构和对象存储格式，因为它们决定了整个系统未来能否可靠地支持多版本、断点续传、去重和存储配额。
